En resumen

Esta es una guía de seguridad para quien tiene un servidor, un sitio, una automatización o un agente de IA en funcionamiento. En octubre de 2026 llegaron juntas dos noticias graves: se filtraron las claves secretas de 8 certificados de la autoridad certificadora eMudhra (una de ellas era literalmente el número 4), y una falla en PHP, llamada PHP2Shell, permite invadir sitios sin contraseña. La guía muestra cómo probar si cada herramienta sigue expuesta, con un script que solo lee y no cambia nada, y cómo actualizar cada capa. Solo necesitas una terminal en la máquina que quieres revisar.

Qué pasó

Dos fallas graves en la misma semana

Una rompe la confianza del candado de HTTPS fuera del navegador. La otra abre los sitios PHP a una invasión sin inicio de sesión.

1. eMudhra: claves de certificado que cabían en un número pequeño

8

certificados intermedios

De la autoridad certificadora eMudhra, creados en una ceremonia el 30/04/2025: 6 para sitios (TLS) y 2 para firmar programas. Las cadenas pasan por la raíz emSign ECC Root CA – G3 y por la cruzada AAA Certificate Services (Sectigo).

4

una de las claves secretas

Las claves P-384 deberían ser números gigantes. Salieron menores que 256: 4, 56, 66, 115, 155, 156, 230 y 237. Cualquiera las encuentra en menos de un segundo. Descubierto el 17/10/2026 por el investigador "Wayne".

?

por qué es grave

Con la clave de una autoridad certificadora de confianza se puede emitir un HTTPS "válido" para cualquier sitio y colocarse en medio de la conexión. Hasta el 21/10 no había explotación confirmada, pero las claves son públicas.

✅ Ya protegidos

Navegadores: Chrome y Firefox (17/10), Microsoft (20/10), Apple (22/10). Firefox corregido: 158.0.1 (NSS 3.131.1).

⚠ Te necesitan a ti

Todo lo que no es un navegador y tiene su propia lista de certificados: curl antiguo, Python (certifi), Node, Go, Docker, n8n, agentes de IA, apps Electron, programas en Rust, equipos sin actualizaciones.

2. PHP2Shell: invasión de sitios PHP sin contraseña

Qué es

Dos fallas críticas en PHP (CVE-2026-109618 y CVE-2026-109619) que permiten ejecutar comandos en el servidor sin iniciar sesión. Aviso del equipo de PHP del 21/10/2026.

Quién está expuesto

Toda instalación de PHP que sirve páginas: PHP-FPM, Apache con mod_php, php-cgi, FrankenPHP y LiteSpeed. Mayor riesgo en mod_php. Incluye la mayoría de los sitios WordPress.

Versiones corregidas

8.5.12 · 8.4.27 · 8.3.36 · 8.2.35. Detalles y qué hacer en PHP2Shell.

Auditar · prueba la conexión real

No basta con ver la versión: prueba si la herramienta se conecta

Los sitios de prueba de abajo usan certificados de las cadenas comprometidas. Si la herramienta se conecta, todavía confía en las claves rotas. Si da error de certificado, está protegida.

Prueba de 10 segundos (curl)

curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
# "SSL certificate problem" = protegido
# mostró la página        = EXPUESTO

Node y Python, de la misma forma

node -e "require('https').get('https://dv-g3b-emudhra.we-have-a-problem.com/',r=>{console.log('EXPOSTO');process.exit()}).on('error',e=>{console.log(/CERT|ISSUER/.test(e.code)?'protegido':'SEM TESTE',e.code);process.exit()})"

python3 -c "import ssl,urllib.request as u,urllib.error as E
try:
  import certifi; ctx=ssl.create_default_context(cafile=certifi.where())
except ImportError: ctx=ssl.create_default_context()
try: u.urlopen('https://dv-g3b-emudhra.we-have-a-problem.com/',context=ctx); print('EXPOSTO')
except E.HTTPError: print('EXPOSTO')
except Exception as e: print('protegido' if 'CERTIFICATE_VERIFY_FAILED' in str(e) else 'SEM TESTE', e)"

Un error de red (ENOTFOUND, timeout) no es "protegido". Ante la duda, usa audita.sh.

Windows y macOS

audita.sh es para Linux. En Windows (PowerShell) y en macOS (Terminal), la prueba rápida es el mismo curl: curl.exe https://dv-g3b-emudhra.we-have-a-problem.com/ (Windows) o curl https://dv-g3b-emudhra.we-have-a-problem.com/ (macOS), y lo mismo para la cadena dv-g3b-aaa-emudhra. Error de certificado = protegido. Si tienes Node o Python instalados, ejecuta también las pruebas de arriba.

Prueba las dos cadenas. En nuestra auditoría, varias herramientas rechazaban la cadena AAA y aceptaban la G3 (o al revés). Una sola prueba puede dar una falsa sensación de seguridad. Y un error de red (DNS, timeout) no es "protegido": es "sin prueba".

El script audita.sh: todo de una vez, solo lectura

Prueba la conexión real con curl, wget, cada Node que encuentre en el disco (incluido el Node embebido en herramientas), el Python del sistema, cada entorno Python (venv) con su certifi y, por dentro, cada contenedor Docker en ejecución. También lista el certifi desactualizado y las versiones de Node y Go. No instala, no modifica y no escribe nada.

1

Descarga el script y léelo antes de ejecutarlo

Regla de oro: nunca ejecutes un script de internet sin mirar lo que hace. Este tiene unas 200 líneas, comentadas.

curl -fsSLO https://raw.githubusercontent.com/inematds/auditoria-seguranca/main/audita.sh
less audita.sh            # lee
chmod +x audita.sh

O clona el repositorio: git clone https://github.com/inematds/auditoria-seguranca.

2

Ejecútalo en la máquina

Sin sudo audita tu usuario (y los contenedores, si estás en el grupo docker). Con sudo ve también las carpetas de otros usuarios. La búsqueda en el disco tarda hasta 3 minutos; --rapido se salta esa parte.

./audita.sh                 # completo
sudo ./audita.sh            # incluye contenedores Docker y otros usuarios
./audita.sh --rapido        # sin buscar venvs y Node en el disco
./audita.sh --sem-docker    # no entra en los contenedores

Con sudo, el Node instalado por el nvm de tu usuario no queda en la ruta estándar; aun así lo encuentra la búsqueda en el disco (en ese caso no uses --rapido).

Fragmento de ejemplo (la salida real tiene más líneas; el script escribe en portugués). G3 y AAA son los dos "caminos de confianza" probados: cada certificado de sitio lo firma un intermedio, que a su vez lo firma una raíz en la que confía tu programa.

  • SEM TESTE (sin prueba): no se pudo probar (red, DNS, timeout). Repite antes de concluir.

Código de salida: 0 nada expuesto, 1 hay EXPOSTO, 2 hay una prueba que no se ejecutó. Se puede usar en monitoreo.

# o una lista (un destino por línea; no versiones ese archivo)

Corrige, reinicia y ejecuta de nuevo

La auditoría solo termina cuando el resumen muestra 0 EXPOSTO · 0 SEM TESTE en todas las máquinas. Un proceso que ya estaba en ejecución guarda la lista antigua en memoria: actualizar sin reiniciar no resuelve nada.

Cómo actualizar · capa por capa

Cada herramienta puede tener su propia lista de certificados de confianza. El ca-certificates del sistema protege a curl y a quien usa la lista del sistema. Node, Python con certifi, Go, Electron, Rust y cada contenedor tienen la suya.

1

Sistema (ca-certificates)

# Ubuntu / Debian
sudo apt update && sudo apt install --only-upgrade ca-certificates
dpkg-query -W ca-certificates          # confirma la versión
# Alpine
apk upgrade --no-cache ca-certificates
# Fedora / RHEL
sudo dnf upgrade ca-certificates

Deja activada la actualización automática (unattended-upgrades en Ubuntu/Debian). En nuestro caso fue ella la que corrigió el sistema sola.

2

Python: el certifi de cada entorno

requests y muchos paquetes usan certifi, no la lista del sistema. Cada venv tiene el suyo. audita.sh lista los desactualizados.

/ruta/del/venv/bin/python -m pip install -U certifi pip
python3 -c "import certifi; print(certifi.__version__, certifi.where())"  # 2026.10.19 o superior
# herramientas instaladas con pipx / uv tool
pipx upgrade-all        # o: pipx runpip <app> install -U certifi
uv self update          # uv 0.13.4 o superior
uv tool upgrade --all

Atención con el Python "del sistema": si aparece EXPOSTO en el modo certifi, hay un certifi instalado con pip --user en tu carpeta (~/.local/lib/python3.X/). La ruta que muestra el comando de arriba indica cuál es. En Ubuntu 24.04 y Debian 12+ pip se niega a modificar ahí ("externally-managed-environment"); como el cambio queda solo en tu carpeta de usuario, usa:

python3 -m pip install --user --break-system-packages -U certifi

El certifi del paquete del sistema (/usr/lib/python3/dist-packages) no necesita esto: en Debian/Ubuntu apunta a la lista de ca-certificates.

3

Node: cambia de versión (Node 20 no tiene corrección)

Node trae la lista de certificados dentro del propio programa. Actualizar el sistema no cambia nada para él.

# con nvm
nvm install 22 && nvm alias default 22     # 22.23.4 o superior
# con el repositorio NodeSource (apt): está separado por versión.
# Si estás en el 20, cambia el repositorio al 22 antes de instalar:
curl -fsSLo nodesource_setup.sh https://deb.nodesource.com/setup_22.x
less nodesource_setup.sh                  # lee
sudo bash nodesource_setup.sh && sudo apt install -y nodejs
# ¿ya estás en el 22 o 24? basta con actualizar
sudo apt update && sudo apt install --only-upgrade nodejs
node -v

Paliativo para quien no puede cambiar hoy (probado por nosotros): hacer que Node use la lista del sistema ya actualizada. Solo funciona si ca-certificates está corregido. --use-system-ca no sirve: suma las dos listas y siguió EXPOSTO en nuestra prueba.

export NODE_OPTIONS=--use-openssl-ca   # en el servicio/entorno de la app; luego reinicia

El Node descargado desde nvm o nodejs.org puede no encontrar la lista del sistema por sí solo: si la prueba da error en todo, agrega SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt y confirma con audita.sh. NODE_OPTIONS es la variable de entorno que pasa opciones a todo Node iniciado ahí (en systemd: Environment=NODE_OPTIONS=--use-openssl-ca; en Docker: environment: del compose).

Busca también Node embebido: Playwright, los agentes de IA y las apps traen su propio Node. audita.sh encuentra esos binarios en el disco; actualiza la herramienta que los trajo.

4

Go: actualiza y recompila

Un programa Go ya compilado lleva la regla antigua. Instala Go 1.27.3 o 1.26.10 y genera el binario de nuevo (go build). Programas Go de terceros: actualiza a la versión que publiquen después del 21/10.

5

Docker: cada contenedor es una máquina

El contenedor no usa el ca-certificates del servidor. Imagen antigua = lista antigua.

# imágenes listas (de Docker Hub, GHCR...)
docker compose pull && docker compose up -d

# imágenes que construyes tú: descarga la base nueva y reconstruye
docker compose build --pull --no-cache && docker compose up -d

En el Dockerfile, cambia la base node:20 por node:22 (o 24) y actualiza la lista durante la construcción:

FROM node:22-bookworm-slim
RUN apt-get update && apt-get install -y --only-upgrade ca-certificates && rm -rf /var/lib/apt/lists/*
# Alpine: RUN apk upgrade --no-cache ca-certificates
6

n8n: respalda y luego actualiza

n8n corre sobre Node. Versión antigua = Node antiguo dentro del contenedor.

# 1) encuentra el nombre del volumen (el compose suele poner el nombre de la carpeta al frente)
docker volume ls | grep n8n                 # ej.: meuprojeto_n8n_data
# 2) detén n8n y haz el respaldo (con él detenido la base de datos no queda a medias)
docker compose stop n8n
docker run --rm -v meuprojeto_n8n_data:/data -v "$PWD":/bk alpine tar czf /bk/n8n-backup.tgz -C /data .
# 3) actualiza
docker compose pull n8n && docker compose up -d n8n
Trampa del docker-compose antiguo (1.29): al levantar la imagen nueva puede fallar con KeyError: 'ContainerConfig' y dejar n8n detenido. Elimina antes el contenedor antiguo (los datos quedan en el volumen): docker-compose rm -f -s n8n && docker-compose up -d n8n. Mejor aún: migra a docker compose v2.

Otras formas de guardar los datos: si n8n usa una carpeta montada (ej.: ./n8n_data o ~/.n8n), copia la carpeta con él detenido; si usa Postgres, haz el pg_dump de la base. En todos los casos guarda junto la clave de cifrado (N8N_ENCRYPTION_KEY o el archivo config de la carpeta de n8n): sin ella las credenciales guardadas no se recuperan.

Después de actualizar, revisa el log (docker compose logs n8n). Los saltos grandes de versión pueden traer avisos nuevos, como el del ejecutor de Python del nodo Code.

7

Windows, macOS, celular y apps

  • Windows: Windows Update (corrección de Microsoft del 20/10).
  • macOS / iPhone: actualización del sistema (Apple, 22/10).
  • Navegadores: reinicia el navegador para aplicar; Firefox 158.0.1 o superior.
  • Apps Electron (VS Code, Slack, Discord y otras): actualiza cada app. Quien desarrolla: Electron 44.9.1 / 43.8.1 / 42.11.16.
  • Rust: cargo update -p rustls-webpki -p webpki-roots y recompila.
8

Reinicia los servicios

Un programa que ya está corriendo retuvo la lista antigua en memoria. Reinicia bots, APIs, workers, agentes y n8n.

sudo systemctl restart <servico>   # servicios del sistema
pm2 restart all                     # apps Node administradas por pm2
docker compose up -d                # contenedores: los recrea con la imagen nueva

Atención: docker compose restart solo reinicia el mismo contenedor, con la imagen vieja. Después de un pull o un build, lo correcto es docker compose up -d.

Y ejecuta audita.sh de nuevo.

Caso real

Auditamos nuestros servidores. El sistema estaba bien. Lo demás, no.

En la madrugada del 23/10/2026 auditamos 6 servidores con este método. Sin nombres ni direcciones: lo que importa es el patrón.

Lo que ya estaba bien

El ca-certificates de los 6 servidores ya estaba corregido por la actualización automática. curl rechazaba las cadenas malas.

Lo que seguía expuesto

Node, entornos Python (certifi) y contenedores, incluido n8n, seguían confiando en las claves rotas.

Lo que corregimos

  • Node 20 → 22
  • certifi de los entornos Python
  • Node embebido de un agente
  • n8n 2.4.8 → 2.44.6 (con respaldo)
  • 4 contenedores reconstruidos

Dos trampas de infraestructura

1. docker-compose antiguo

n8n no arrancó después del pull: docker-compose 1.29 dio KeyError 'ContainerConfig' con la imagen nueva y el servicio quedó detenido unos minutos. Se resolvió eliminando el contenedor antiguo antes del up.

2. Archivo montado desde /tmp

Un nginx en un contenedor montaba su configuración desde un archivo en /tmp. La limpieza de /tmp convirtió la ruta en una carpeta vacía, y al recrear el contenedor nginx no arrancó. La configuración montada debe vivir en una carpeta permanente.

¿Y la máquina de desarrollo? También le ejecutamos audita.sh: el sistema y curl estaban protegidos, pero el Node del sistema, el Node embebido de Playwright, el certifi del Python del usuario, varios entornos Python y decenas de contenedores locales (bases de datos, paneles, herramientas de IA) todavía se conectaban. Es el mismo patrón: lo que no es el sistema se queda atrás. En un servidor ya corregido, el script aún señaló un Node antiguo en una carpeta de respaldo (.bak) olvidada después del cambio de versión: no se ejecutaba, pero es el tipo de resto que alguien ejecuta por error. Borra las copias antiguas que no uses.
PHP2Shell

Tu sitio PHP puede ser invadido sin contraseña

Aviso del equipo de PHP del 21/10/2026: dos fallas críticas permiten ejecutar código en el servidor sin iniciar sesión. La falla está en PHP, antes de que WordPress o cualquier aplicación abra la página. Un plugin de seguridad no la detiene.

Las dos fallas

  • CVE-2026-109618: el manejo de falta de memoria interrumpe PHP con datos de la solicitud a medias, y la limpieza trata esos datos como válidos.
  • CVE-2026-109619: un estado interno de la solicitud sobrevive después de liberar la memoria, y la siguiente solicitud del mismo proceso usa ese estado viejo.

Quién está expuesto

  • Toda instalación de PHP que sirve páginas: PHP-FPM, Apache con mod_php, php-cgi, FrankenPHP, LiteSpeed.
  • Mayor riesgo en mod_php: hay un ataque demostrado que funciona antes de que corra cualquier código de la aplicación.
  • PHP corre debajo de cerca de 7 de cada 10 sitios, incluida la mayoría de los WordPress.

Tu caso, en tres situaciones

1. Plataforma lista

Shopify, Wix, Squarespace: PHP es responsabilidad de la empresa. Revisa el aviso de seguridad de la plataforma; si no lo encuentras, pregunta al soporte.

2. WordPress en hosting

Prueba el sitio (paso de abajo) y mira la versión de PHP en el panel del hosting. Si está por debajo de la versión corregida: pide al proveedor que actualice hoy.

3. Servidor propio (VPS)

Es contigo y es urgente: los ataques empezaron incluso antes de que saliera la corrección. Actualiza, reinicia y busca señales de intrusión.

1

Prueba: el verificador de OpenAI

OpenAI publicó el php2shell-checker (licencia Apache 2.0). Lee la versión que el sitio anuncia en los encabezados; no envía ningún ataque. Necesita git y Node instalados en tu computadora (no en el servidor).

git clone https://github.com/openai/php2shell-checker && cd php2shell-checker
node phpcheck.js "https://seusite.com.br"
# OK (0) · POTENTIALLY VULNERABLE (1) · UNKNOWN (3)

O pídele a tu agente (Claude Code, Codex): "ejecuta php2shell-checker solo contra mi sitio y explícame el resultado". UNKNOWN no es luz verde: el sitio oculta la versión; confírmala en el panel o en el servidor.

2

En el servidor: mira la versión real

php -v
php-fpm8.3 -v                       # ajusta el número de la versión
apt changelog php8.3-fpm | head -30  # Debian/Ubuntu: busca CVE-2026-109618
Cuidado con el número. Las distribuciones Linux y los proveedores de soporte extendido (LTS) recibieron la corrección antes y pueden aplicarla manteniendo el número antiguo (backport). Por eso el encabezado y el verificador no ven los backports: "versión por debajo de la corregida" significa "investiga en el changelog de tu proveedor", no necesariamente "vulnerable".
3

Corrige: actualiza y reinicia todos los procesos

  • Versiones corregidas: 8.5.12, 8.4.27, 8.3.36, 8.2.35 (o el paquete corregido de tu distribución).
  • PHP 8.1 y anteriores ya no reciben actualizaciones del proyecto PHP. Algunas distribuciones y proveedores LTS tienen la corrección: pregúntales o sube a una versión con soporte. Por la gravedad, el equipo de PHP publicó correcciones mínimas en código fuente para 7.4, 8.0 y 8.1, para quien compila.
sudo apt update
apt list --upgradable 2>/dev/null | grep -i php   # mira qué va a cambiar
sudo apt install --only-upgrade $(dpkg -l 'php*' | awk '/^ii/{print $2}')   # solo los paquetes PHP instalados
sudo systemctl restart php8.3-fpm    # o apache2, si usas mod_php

¿Usas el repositorio PPA ondrej/php (común para tener varias versiones)? También debe tener la versión corregida; confírmalo con php -v después. mod_php es PHP corriendo dentro de Apache; PHP-FPM es PHP como servicio separado, usado con nginx o Apache.

4

¿No puedes actualizar ahora? Reduce la exposición

El propio equipo de PHP advierte: estas medidas reducen caminos de ataque conocidos, no hacen segura la instalación. Solo la actualización lo resuelve. Aplícalas en php.ini, en el pool de FPM o en la configuración del servidor (no con ini_set() ni .user.ini) y reinicia todos los workers.

# en el pool de FPM (ej.: /etc/php/8.3/fpm/pool.d/www.conf), que la aplicación no puede cambiar:
php_admin_value[memory_limit] = -1
php_admin_value[post_max_size] = 8M          # 32M si el sitio necesita subir archivos
php_admin_value[upload_max_filesize] = 6M    # siempre por debajo de post_max_size
php_admin_flag[session.upload_progress.enabled] = off
# solo en PHP 8.5:
php_admin_flag[fatal_error_backtraces] = off
  • memory_limit = -1 (contra CVE-2026-109618) quita el límite de memoria de PHP. Eso cierra el camino de ataque, pero un script con errores puede consumir toda la RAM del servidor. Por eso el equipo de PHP recomienda poner un límite fuera de PHP: el límite de memoria del contenedor (Docker) o del servicio (cgroup, en systemd MemoryMax=), de preferencia terminando solo el proceso afectado.
  • No uses RLIMIT_AS/RLIMIT_DATA (límites de memoria de ulimit) en su lugar: pueden provocar justamente la falla de memoria vulnerable.
  • session.upload_progress.enabled y fatal_error_backtraces desactivados (contra CVE-2026-109619) bloquean solo los caminos confirmados, no otras variantes.
5

¿Quedó expuesto? Busca señales de intrusión

# archivos .php creados o modificados en los últimos 7 días dentro del sitio
find /var/www -name '*.php' -mtime -7 -ls
# .php dentro de la carpeta de uploads de WordPress (allí no debería haber ninguno)
find /var/www -path '*wp-content/uploads*' -name '*.php' -ls

Lo que más vale la pena hacer

La inteligencia artificial está encontrando fallas antiguas cada vez más rápido. La defensa es rutina, no susto.

🤖 Agentes de IA y curl | bash

  • Un instalador del tipo curl ... | bash ejecuta código de internet con tu usuario. Descárgalo primero, léelo, y solo entonces ejecútalo.
  • Verifica el checksum (sha256sum archivo) o la firma publicada por el proyecto.
  • Fija versiones (package-lock.json, requirements.txt con versión, imagen Docker con tag) y actualiza a propósito, no por casualidad.
  • Agente con acceso a la terminal: ejecútalo en una carpeta aislada o un contenedor, sin secretos a la vista.

📅 Lista de verificación mensual (30 minutos)

  • Actualizaciones del sistema aplicadas y actualización automática activada.
  • Node, Python (certifi), Go e imágenes Docker en versiones con soporte.
  • ./audita.sh en todas las máquinas: resumen en cero.
  • Respaldo probado: restauraste de verdad, no solo "existe".
  • Línea de versión aún con soporte (Node 20 y PHP 8.1 ya no lo tienen).

🔎 Vigila los certificados de tu dominio

Todo certificado emitido queda en un registro público (Certificate Transparency). Busca tu dominio en crt.sh y revisa si apareció un certificado que no pediste. Un registro CAA en el DNS indica qué autoridades certificadoras pueden emitir para tu dominio.

dig CAA seudominio.com.br +short

⚙️ CI/CD y secretos

  • Reconstruye las imágenes en el pipeline con --pull: una imagen vieja en caché trae una lista vieja.
  • Ejecuta audita.sh como etapa del despliegue; una salida distinta de 0 bloquea el despliegue.
  • Nada de claves en el código ni en git (.env fuera del repositorio); si una clave se filtró, cámbiala, no basta con borrarla.
  • Para sitios, el método blinda-site de INEMA revisa encabezados, dependencias, secretos y base de datos con un agente de IA, sin tocar el sitio en producción.
Glosario

Las palabras de esta guía

Autoridad certificadora (CA)

Empresa que firma los certificados HTTPS. Es la "notaría" que dice: este sitio es realmente quien dice ser.

Raíz, intermedio, cadena

La raíz es la firma madre en la que confía tu programa. Ella firma intermedios, que firman los sitios. La secuencia es la cadena. Las claves filtradas son de intermedios.

P-384

Tipo de clave de curva elíptica. Una buena clave P-384 es un número de más de 100 dígitos; las de eMudhra eran menores que 256.

ca-certificates

Paquete de Linux con la lista de autoridades certificadoras de confianza del sistema. Lo usan curl, wget y muchos programas.

certifi

Paquete de Python con una lista propia de autoridades certificadoras. requests lo usa a él, no a la del sistema.

venv

Entorno Python aislado de un proyecto, con sus propios paquetes (y su propio certifi).

Contenedor (Docker)

Una "máquina" liviana dentro del servidor, con sistema y lista de certificados propios. Imagen antigua = lista antigua.

pm2 · systemd

Administradores que mantienen programas corriendo en el servidor y los reinician.

CVE

Número público de una falla de seguridad, usado para buscar la corrección (ej.: CVE-2026-109618).
