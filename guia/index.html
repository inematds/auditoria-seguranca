Atualize e audite seus sistemas hoje

O navegador já te protege. O seu servidor, o seu Python, o seu Node, os seus containers e o seu n8n talvez não. Aqui está como testar de verdade e como corrigir cada camada.

Testar agora Como atualizar
Em resumo

Este é um guia de segurança para quem tem servidor, site, automação ou agente de IA rodando. Em outubro de 2026 vieram duas notícias graves juntas: vazaram as chaves secretas de 8 certificados da certificadora eMudhra (uma delas era literalmente o número 4), e uma falha no PHP, chamada PHP2Shell, deixa invadir sites sem senha. O guia mostra como testar se cada ferramenta ainda está exposta, com um script que só lê e não muda nada, e como atualizar cada camada. Precisa só de um terminal na máquina que você quer conferir.

O que houve

Duas falhas graves na mesma semana

Uma quebra a confiança do cadeado do HTTPS fora do navegador. A outra abre sites PHP para invasão sem login.

1. eMudhra: chaves de certificado que cabiam num número pequeno

8

certificados intermediários

Da certificadora eMudhra, criados numa cerimônia em 30/04/2025: 6 para sites (TLS) e 2 para assinar programas. As cadeias passam pela raiz emSign ECC Root CA – G3 e pela cruzada AAA Certificate Services (Sectigo).

4

uma das chaves secretas

As chaves P-384 deveriam ser números gigantes. Saíram menores que 256: 4, 56, 66, 115, 155, 156, 230 e 237. Qualquer um acha em menos de um segundo. Descoberto em 17/10/2026 pelo pesquisador "Wayne".

?

por que é grave

Com a chave de uma certificadora confiável dá para emitir um HTTPS "válido" para qualquer site e ficar no meio da conexão. Até 21/10 não havia exploração confirmada, mas as chaves são públicas.

✅ Já protegidos

Navegadores: Chrome e Firefox (17/10), Microsoft (20/10), Apple (22/10). Firefox corrigido: 158.0.1 (NSS 3.131.1).

⚠ Precisam de você

Tudo o que não é navegador e tem lista própria de certificados: curl antigo, Python (certifi), Node, Go, Docker, n8n, agentes de IA, apps Electron, programas em Rust, aparelhos sem atualização.

2. PHP2Shell: invasão de site PHP sem senha

O que é

Duas falhas críticas no PHP (CVE-2026-109618 e CVE-2026-109619) que permitem executar comandos no servidor sem login. Aviso do time do PHP em 21/10/2026.

Quem está exposto

Toda instalação PHP que atende páginas: PHP-FPM, Apache com mod_php, php-cgi, FrankenPHP e LiteSpeed. Risco maior no mod_php. Inclui a maioria dos sites WordPress.

Versões corrigidas

8.5.12 · 8.4.27 · 8.3.36 · 8.2.35. Detalhes e o que fazer em PHP2Shell.

Auditar · teste a conexão real

Não basta ver a versão: teste se a ferramenta conecta

Os sites de teste abaixo usam certificados das cadeias comprometidas. Se a ferramenta conecta, ela ainda confia nas chaves quebradas. Se dá erro de certificado, está protegida.

Teste de 10 segundos (curl)

curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
# "SSL certificate problem" = protegido
# mostrou a página        = EXPOSTO

Node e Python, do mesmo jeito

node -e "require('https').get('https://dv-g3b-emudhra.we-have-a-problem.com/',r=>{console.log('EXPOSTO');process.exit()}).on('error',e=>{console.log(/CERT|ISSUER/.test(e.code)?'protegido':'SEM TESTE',e.code);process.exit()})"

python3 -c "import ssl,urllib.request as u,urllib.error as E
try:
  import certifi; ctx=ssl.create_default_context(cafile=certifi.where())
except ImportError: ctx=ssl.create_default_context()
try: u.urlopen('https://dv-g3b-emudhra.we-have-a-problem.com/',context=ctx); print('EXPOSTO')
except E.HTTPError: print('EXPOSTO')
except Exception as e: print('protegido' if 'CERTIFICATE_VERIFY_FAILED' in str(e) else 'SEM TESTE', e)"

Erro de rede (ENOTFOUND, timeout) não é "protegido". Na dúvida, use o audita.sh.

Windows e macOS

O audita.sh é para Linux. No Windows (PowerShell) e no macOS (Terminal), o teste rápido é o mesmo curl: curl.exe https://dv-g3b-emudhra.we-have-a-problem.com/ (Windows) ou curl https://dv-g3b-emudhra.we-have-a-problem.com/ (macOS), e o mesmo para a cadeia dv-g3b-aaa-emudhra. Erro de certificado = protegido. Se você tem Node ou Python instalados, rode também os testes acima.

Teste as duas cadeias. Na nossa auditoria, várias ferramentas recusavam a cadeia AAA e aceitavam a G3 (ou o contrário). Um teste só pode dar falsa sensação de segurança. E erro de rede (DNS, timeout) não é "protegido": é "sem teste".

O script audita.sh: tudo de uma vez, só leitura

Ele testa a conexão real com curl, wget, cada Node encontrado no disco (inclusive Node embutido em ferramentas), o Python do sistema, cada ambiente Python (venv) com o certifi dele e, por dentro, cada container Docker em execução. Também lista o certifi desatualizado e as versões de Node e Go. Não instala, não altera e não grava nada.

1

Baixe o script e leia antes de rodar

Regra de ouro: nunca rode script da internet sem olhar o que ele faz. Este tem cerca de 200 linhas, comentadas.

curl -fsSLO https://raw.githubusercontent.com/inematds/auditoria-seguranca/main/audita.sh
less audita.sh            # leia
chmod +x audita.sh

Ou clone o repositório: git clone https://github.com/inematds/auditoria-seguranca.

2

Rode na máquina

Sem sudo ele audita o seu usuário (e os containers, se você está no grupo docker). Com sudo ele enxerga também as pastas de outros usuários. A busca no disco leva até 3 minutos; --rapido pula essa parte.

./audita.sh                 # completo
sudo ./audita.sh            # inclui containers Docker e outros usuários
./audita.sh --rapido        # sem procurar venvs e Node no disco
./audita.sh --sem-docker    # não entra nos containers

Com sudo, o Node instalado pelo nvm do seu usuário não fica no caminho padrão; ele ainda é achado pela busca no disco (não use --rapido nesse caso).

Trecho de exemplo (a saída real tem mais linhas; o script escreve em português). G3 e AAA são os dois "caminhos de confiança" testados: cada certificado de site é assinado por um intermediário, que é assinado por uma raiz que o seu programa confia.

  • EXPOSTO: conectou. Corrija essa camada (seção Atualizar).
  • protegido: recusou por erro de certificado.
  • SEM TESTE: não deu para testar (rede, DNS, timeout). Repita antes de concluir.

Código de saída: 0 nada exposto, 1 há EXPOSTO, 2 há teste que não rodou. Dá para usar em monitoramento.

Audite vários servidores por SSH

O script vai pelo próprio SSH e roda lá, sem copiar nada para o servidor. Use acesso por chave.

# ou uma lista (um destino por linha; não versione esse arquivo)

5

Corrija, reinicie e rode de novo

A auditoria só termina quando o resumo mostra 0 EXPOSTO · 0 SEM TESTE em todas as máquinas. Processo que já estava rodando guarda a lista antiga na memória: atualizar sem reiniciar não resolve.

Como atualizar · camada por camada

Atualizar o sistema não basta

Cada ferramenta pode ter a própria lista de certificados confiáveis. O ca-certificates do sistema protege o curl e quem usa a lista do sistema. Node, Python com certifi, Go, Electron, Rust e cada container têm a sua.

1

Sistema (ca-certificates)

# Ubuntu / Debian
sudo apt update && sudo apt install --only-upgrade ca-certificates
dpkg-query -W ca-certificates          # confira a versão
# Alpine
apk upgrade --no-cache ca-certificates
# Fedora / RHEL
sudo dnf upgrade ca-certificates

Deixe a atualização automática ligada (unattended-upgrades no Ubuntu/Debian). No nosso caso foi ela que corrigiu o sistema sozinha.

2

Python: o certifi de cada ambiente

O requests e muitos pacotes usam o certifi, não a lista do sistema. Cada venv tem o seu. O audita.sh lista os desatualizados.

/caminho/do/venv/bin/python -m pip install -U certifi pip
python3 -c "import certifi; print(certifi.__version__, certifi.where())"  # 2026.10.19 ou mais
# ferramentas instaladas com pipx / uv tool
pipx upgrade-all        # ou: pipx runpip <app> install -U certifi
uv self update          # uv 0.13.4 ou mais
uv tool upgrade --all

Atenção ao Python "do sistema": se aparecer EXPOSTO no modo certifi, existe um certifi instalado com pip --user na sua pasta (~/.local/lib/python3.X/). O caminho mostrado pelo comando acima diz qual é. No Ubuntu 24.04 e no Debian 12+ o pip recusa mexer ali ("externally-managed-environment"); como a mudança fica só na sua pasta de usuário, use:

python3 -m pip install --user --break-system-packages -U certifi

O certifi do pacote do sistema (/usr/lib/python3/dist-packages) não precisa disso: no Debian/Ubuntu ele aponta para a lista do ca-certificates.

3

Node: troque de versão (Node 20 não tem correção)

O Node traz a lista de certificados dentro do próprio programa. Atualizar o sistema não muda nada para ele.

# com nvm
nvm install 22 && nvm alias default 22     # 22.23.4 ou mais
# com o repositório NodeSource (apt): ele é separado por versão.
# Se está no 20, troque o repositório para o 22 antes de instalar:
curl -fsSLo nodesource_setup.sh https://deb.nodesource.com/setup_22.x
less nodesource_setup.sh                  # leia
sudo bash nodesource_setup.sh && sudo apt install -y nodejs
# já está no 22 ou 24? basta atualizar
sudo apt update && sudo apt install --only-upgrade nodejs
node -v

Paliativo para quem não consegue trocar hoje (testado por nós): mandar o Node usar a lista do sistema já atualizada. Só funciona se o ca-certificates estiver corrigido. --use-system-ca não serve: ele soma as duas listas e continuou EXPOSTO no nosso teste.

export NODE_OPTIONS=--use-openssl-ca   # no serviço/ambiente do app; depois reinicie

Node baixado do nvm ou do nodejs.org pode não achar a lista do sistema sozinho: se o teste der erro em tudo, acrescente SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt e confirme com o audita.sh. NODE_OPTIONS é a variável de ambiente que passa opções para todo Node iniciado ali (no systemd: Environment=NODE_OPTIONS=--use-openssl-ca; no Docker: environment: do compose).

Procure também Node embutido: o Playwright, agentes de IA e apps trazem um Node próprio. O audita.sh acha esses binários no disco; atualize a ferramenta que os trouxe.

4

Go: atualize e recompile

Programa Go já compilado carrega a regra antiga. Instale Go 1.27.3 ou 1.26.10 e gere o binário de novo (go build). Programas Go de terceiros: atualize para a versão que eles lançarem depois de 21/10.

5

Docker: cada container é uma máquina

O container não usa o ca-certificates do servidor. Imagem antiga = lista antiga.

# imagens prontas (do Docker Hub, GHCR...)
docker compose pull && docker compose up -d

# imagens que você constrói: puxe a base nova e reconstrua
docker compose build --pull --no-cache && docker compose up -d

No Dockerfile, troque a base node:20 por node:22 (ou 24) e atualize a lista na construção:

FROM node:22-bookworm-slim
RUN apt-get update && apt-get install -y --only-upgrade ca-certificates && rm -rf /var/lib/apt/lists/*
# Alpine: RUN apk upgrade --no-cache ca-certificates
6

n8n: backup, depois atualize

O n8n roda em Node. Versão antiga = Node antigo dentro do container.

# 1) ache o nome do volume (o compose costuma pôr o nome da pasta na frente)
docker volume ls | grep n8n                 # ex.: meuprojeto_n8n_data
# 2) pare o n8n e faça o backup (com ele parado o banco não sai pela metade)
docker compose stop n8n
docker run --rm -v meuprojeto_n8n_data:/data -v "$PWD":/bk alpine tar czf /bk/n8n-backup.tgz -C /data .
# 3) atualize
docker compose pull n8n && docker compose up -d n8n
Armadilha do docker-compose antigo (1.29): ao subir a imagem nova ele pode falhar com KeyError: 'ContainerConfig' e deixar o n8n parado. Remova o container antigo antes (os dados ficam no volume): docker-compose rm -f -s n8n && docker-compose up -d n8n. Melhor ainda: migre para o docker compose v2.

Outros jeitos de guardar os dados: se o n8n usa uma pasta montada (ex.: ./n8n_data ou ~/.n8n), copie a pasta com ele parado; se usa Postgres, faça o pg_dump do banco. Em todos os casos guarde junto a chave de criptografia (N8N_ENCRYPTION_KEY ou o arquivo config da pasta do n8n): sem ela as credenciais salvas não voltam.

Depois de atualizar, olhe o log (docker compose logs n8n). Saltos grandes de versão podem trazer avisos novos, como o do executor de Python do nó Code.

7

Windows, macOS, celular e apps

  • Windows: Windows Update (correção da Microsoft de 20/10).
  • macOS / iPhone: atualização do sistema (Apple, 22/10).
  • Navegadores: reinicie o navegador para aplicar; Firefox 158.0.1 ou mais.
  • Apps Electron (VS Code, Slack, Discord e outros): atualize cada app. Quem desenvolve: Electron 44.9.1 / 43.8.1 / 42.11.16.
  • Rust: cargo update -p rustls-webpki -p webpki-roots e recompile.
8

Reinicie os serviços

Programa que já está rodando segurou a lista antiga na memória. Reinicie bots, APIs, workers, agentes e o n8n.

sudo systemctl restart <servico>   # serviços do sistema
pm2 restart all                     # apps Node gerenciados pelo pm2
docker compose up -d                # containers: recria com a imagem nova

Atenção: docker compose restart só reinicia o mesmo container, com a imagem velha. Depois de pull ou build, o certo é docker compose up -d.

E rode o audita.sh de novo.

Caso real

Auditamos nossos servidores. O sistema estava certo. O resto não.

Na madrugada de 23/10/2026 auditamos 6 servidores com este método. Sem nomes nem endereços: o que importa é o padrão.

O que já estava certo

O ca-certificates dos 6 servidores já estava corrigido pela atualização automática. O curl recusava as cadeias ruins.

O que continuava exposto

Node, ambientes Python (certifi) e containers, inclusive o n8n, seguiam confiando nas chaves quebradas.

O que corrigimos

  • Node 20 → 22
  • certifi dos ambientes Python
  • Node embutido de um agente
  • n8n 2.4.8 → 2.44.6 (com backup)
  • 4 containers reconstruídos

Duas armadilhas de infraestrutura

1. docker-compose antigo

O n8n não subiu depois do pull: o docker-compose 1.29 deu KeyError 'ContainerConfig' com a imagem nova e o serviço ficou parado por uns minutos. Resolveu remover o container antigo antes do up.

2. Arquivo montado a partir do /tmp

Um nginx em container montava a configuração de um arquivo em /tmp. A limpeza do /tmp transformou o caminho numa pasta vazia, e ao recriar o container o nginx não subiu. Configuração montada tem que morar numa pasta permanente.

E a máquina de desenvolvimento? Rodamos o audita.sh nela também: o sistema e o curl estavam protegidos, mas o Node do sistema, o Node embutido do Playwright, o certifi do Python do usuário, vários ambientes Python e dezenas de containers locais (bancos, painéis, ferramentas de IA) ainda conectavam. É o mesmo padrão: quem não é o sistema fica para trás. Num servidor já corrigido, o script ainda apontou um Node antigo numa pasta de backup (.bak) esquecida depois da troca de versão: não rodava, mas é o tipo de sobra que alguém executa por engano. Apague cópias antigas que não usa.
PHP2Shell

Seu site PHP pode ser invadido sem senha

Aviso do time do PHP de 21/10/2026: duas falhas críticas permitem executar código no servidor sem login. A falha está no PHP, antes do WordPress ou de qualquer aplicação abrir a página. Plugin de segurança não segura.

As duas falhas

  • CVE-2026-109618: o tratamento de falta de memória interrompe o PHP com dados da requisição pela metade, e a limpeza trata esses dados como válidos.
  • CVE-2026-109619: um estado interno da requisição sobrevive depois de a memória ser liberada, e a requisição seguinte do mesmo processo usa esse estado velho.

Quem está exposto

  • Toda instalação PHP que atende páginas: PHP-FPM, Apache com mod_php, php-cgi, FrankenPHP, LiteSpeed.
  • Risco maior no mod_php: há ataque demonstrado que funciona antes de qualquer código da aplicação rodar.
  • PHP roda por baixo de cerca de 7 em cada 10 sites, inclusive a maioria dos WordPress.

Seu caso, em três situações

1. Plataforma pronta

Shopify, Wix, Squarespace: o PHP é responsabilidade da empresa. Confira o aviso de segurança da plataforma; se não achar, pergunte ao suporte.

2. WordPress em hospedagem

Teste o site (passo abaixo) e veja a versão do PHP no painel da hospedagem. Abaixo da versão corrigida: peça ao provedor para atualizar hoje.

3. Servidor próprio (VPS)

É com você e é urgente: ataques começaram antes mesmo de a correção sair. Atualize, reinicie e procure sinais de invasão.

1

Teste: o verificador da OpenAI

A OpenAI publicou o php2shell-checker (licença Apache 2.0). Ele lê a versão que o site anuncia nos cabeçalhos; não manda ataque. Precisa de git e Node instalados no seu computador (não no servidor).

git clone https://github.com/openai/php2shell-checker && cd php2shell-checker
node phpcheck.js "https://seusite.com.br"
# OK (0) · POTENTIALLY VULNERABLE (1) · UNKNOWN (3)

Ou peça ao seu agente (Claude Code, Codex): "rode o php2shell-checker só contra o meu site e me explique o resultado". UNKNOWN não é sinal verde: o site esconde a versão; confira no painel ou no servidor.

2

No servidor: veja a versão de verdade

php -v
php-fpm8.3 -v                       # ajuste o número da versão
apt changelog php8.3-fpm | head -30  # Debian/Ubuntu: procure CVE-2026-109618
Cuidado com o número. Distribuições Linux e fornecedores de suporte longo (LTS) receberam a correção antes e podem aplicá-la mantendo o número antigo (backport). Por isso o cabeçalho e o verificador não enxergam backport: "versão abaixo da corrigida" quer dizer "investigue no changelog do seu fornecedor", não necessariamente "vulnerável".
3

Corrija: atualize e reinicie todos os processos

  • Versões corrigidas: 8.5.12, 8.4.27, 8.3.36, 8.2.35 (ou o pacote corrigido da sua distribuição).
  • PHP 8.1 e anteriores não recebem mais atualização do projeto PHP. Algumas distribuições e fornecedores LTS têm a correção: pergunte a eles ou suba para uma versão suportada. Pela gravidade, o time do PHP publicou correções mínimas em código-fonte para 7.4, 8.0 e 8.1, para quem compila.
sudo apt update
apt list --upgradable 2>/dev/null | grep -i php   # veja o que vai mudar
sudo apt install --only-upgrade $(dpkg -l 'php*' | awk '/^ii/{print $2}')   # só os pacotes PHP instalados
sudo systemctl restart php8.3-fpm    # ou apache2, se usa mod_php

Usa o repositório PPA ondrej/php (comum para ter várias versões)? Ele também precisa estar com a versão corrigida; confira com php -v depois. mod_php é o PHP rodando dentro do Apache; PHP-FPM é o PHP como serviço separado, usado com nginx ou Apache.

4

Não dá para atualizar agora? Reduza a exposição

O próprio time do PHP avisa: estas medidas reduzem caminhos de ataque conhecidos, não tornam a instalação segura. Só a atualização resolve. Aplique no php.ini, no pool do FPM ou na configuração do servidor (não em ini_set() nem .user.ini) e reinicie todos os workers.

# no pool do FPM (ex.: /etc/php/8.3/fpm/pool.d/www.conf), que a aplicação não consegue mudar:
php_admin_value[memory_limit] = -1
php_admin_value[post_max_size] = 8M          # 32M se o site precisa de upload
php_admin_value[upload_max_filesize] = 6M    # sempre abaixo do post_max_size
php_admin_flag[session.upload_progress.enabled] = off
# só no PHP 8.5:
php_admin_flag[fatal_error_backtraces] = off
  • memory_limit = -1 (contra a CVE-2026-109618) tira o limite de memória do PHP. Isso fecha o caminho de ataque, mas um script com defeito pode consumir toda a RAM do servidor. Por isso o time do PHP recomenda pôr um limite fora do PHP: o limite de memória do container (Docker) ou do serviço (cgroup, no systemd MemoryMax=), de preferência derrubando só o processo afetado.
  • Não use RLIMIT_AS/RLIMIT_DATA (limites de memória do ulimit) no lugar disso: eles podem provocar justamente a falha de memória vulnerável.
  • session.upload_progress.enabled e fatal_error_backtraces desligados (contra a CVE-2026-109619) bloqueiam só os caminhos confirmados, não outras variantes.
5

Ficou exposto? Procure sinais de invasão

# arquivos .php criados ou mudados nos últimos 7 dias dentro do site
find /var/www -name '*.php' -mtime -7 -ls
# .php dentro da pasta de uploads do WordPress (lá não deveria haver nenhum)
find /var/www -path '*wp-content/uploads*' -name '*.php' -ls
# tarefas agendadas que você não criou
crontab -l; sudo crontab -l -u www-data; ls -la /etc/cron.*
# acessos recentes e usuários novos
last -20; tail -5 /etc/passwd
wp user list --role=administrator --path=/var/www/seusite   # WP-CLI; como root, acrescente --allow-root

Achou algo que você não criou: tire o site do ar, troque senhas e chaves, restaure de um backup anterior à invasão.

O que mais vale fazer

A inteligência artificial está achando falhas antigas cada vez mais rápido. A defesa é rotina, não susto.

🤖 Agentes de IA e curl | bash

  • Instalador do tipo curl ... | bash roda código da internet com o seu usuário. Baixe primeiro, leia, e só então rode.
  • Confira o checksum (sha256sum arquivo) ou a assinatura publicada pelo projeto.
  • Fixe versões (package-lock.json, requirements.txt com versão, imagem Docker com tag) e atualize de propósito, não por acaso.
  • Agente com acesso ao terminal: rode em pasta isolada ou container, sem segredos à vista.

📅 Checklist mensal (30 minutos)

  • Atualizações do sistema aplicadas e atualização automática ligada.
  • Node, Python (certifi), Go e imagens Docker nas versões suportadas.
  • ./audita.sh em todas as máquinas: resumo zerado.
  • Backup testado: restaurou de verdade, não só "existe".
  • Linha de versão ainda suportada (Node 20 e PHP 8.1 já não são).

🔎 Vigie os certificados do seu domínio

Todo certificado emitido fica num registro público (Certificate Transparency). Procure seu domínio no crt.sh e veja se apareceu certificado que você não pediu. Um registro CAA no DNS diz quais certificadoras podem emitir para o seu domínio.

dig CAA seudominio.com.br +short

⚙️ CI/CD e segredos

  • Reconstrua as imagens no pipeline com --pull: imagem velha em cache traz lista velha.
  • Rode o audita.sh como etapa do deploy; saída diferente de 0 barra o deploy.
  • Nada de chave no código ou no git (.env fora do repositório); se uma chave vazou, troque, não só apague.
  • Para sites, o método blinda-site do INEMA olha cabeçalhos, dependências, segredos e banco com um agente de IA, sem tocar no site no ar.
Glossário

As palavras deste guia

Certificadora (CA)

Empresa que assina os certificados HTTPS. É o "cartório" que diz: este site é mesmo quem diz ser.

Raiz, intermediário, cadeia

A raiz é a assinatura-mãe que o seu programa confia. Ela assina intermediários, que assinam os sites. A sequência é a cadeia. As chaves vazadas são de intermediários.

P-384

Tipo de chave por curva elíptica. Uma chave P-384 boa é um número com mais de 100 dígitos; as da eMudhra eram menores que 256.

ca-certificates

Pacote do Linux com a lista de certificadoras confiáveis do sistema. Usado pelo curl, wget e muitos programas.

certifi

Pacote Python com uma lista própria de certificadoras. O requests usa ele, não a do sistema.

venv

Ambiente Python isolado de um projeto, com os próprios pacotes (e o próprio certifi).

Container (Docker)

Uma "máquina" leve dentro do servidor, com sistema e lista de certificados próprios. Imagem antiga = lista antiga.

pm2 · systemd

Gerenciadores que mantêm programas rodando no servidor e os reiniciam.

CVE

Número público de uma falha de segurança, usado para procurar a correção (ex.: CVE-2026-109618).
