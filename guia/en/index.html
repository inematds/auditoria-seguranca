Update and audit your systems today

Your browser already protects you. Your server, your Python, your Node, your containers and your n8n may not be. Here is how to really test them and how to fix each layer.

Test now How to update
In short

This is a security guide for anyone running a server, website, automation or AI agent. In October 2026 two serious pieces of news arrived together: the secret keys of 8 certificates from the certificate authority eMudhra leaked (one of them was literally the number 4), and a flaw in PHP, called PHP2Shell, lets attackers break into sites without a password. The guide shows how to test whether each tool is still exposed, using a script that only reads and changes nothing, and how to update each layer. All you need is a terminal on the machine you want to check.

What happened

Two serious flaws in the same week

One breaks the trust behind the HTTPS padlock outside the browser. The other opens PHP sites to break-ins with no login.

1. eMudhra: certificate keys small enough to fit in a tiny number

8

intermediate certificates

From the certificate authority eMudhra, created in a ceremony on 04/30/2025: 6 for websites (TLS) and 2 for signing software. The chains go through the root emSign ECC Root CA – G3 and the cross-signed AAA Certificate Services (Sectigo).

4

one of the secret keys

P-384 keys should be gigantic numbers. These came out smaller than 256: 4, 56, 66, 115, 155, 156, 230 and 237. Anyone can find them in under a second. Discovered on 10/17/2026 by the researcher "Wayne".

?

why it is serious

With the key of a trusted certificate authority, you can issue a "valid" HTTPS certificate for any site and sit in the middle of the connection. Until 10/21 there was no confirmed exploitation, but the keys are public.

✅ Already protected

Browsers: Chrome and Firefox (10/17), Microsoft (10/20), Apple (10/22). Fixed Firefox: 158.0.1 (NSS 3.131.1).

⚠ Need your action

Everything that is not a browser and keeps its own list of certificates: old curl, Python (certifi), Node, Go, Docker, n8n, AI agents, Electron apps, Rust programs, devices with no updates.

2. PHP2Shell: breaking into a PHP site with no password

What it is

Two critical flaws in PHP (CVE-2026-109618 and CVE-2026-109619) that allow running commands on the server without logging in. Advisory from the PHP team on 10/21/2026.

Who is exposed

Every PHP installation that serves pages: PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP and LiteSpeed. Higher risk with mod_php. This includes most WordPress sites.

Fixed versions

8.5.12 · 8.4.27 · 8.3.36 · 8.2.35. Details and what to do in PHP2Shell.

Audit · test the real connection

Checking the version is not enough: test whether the tool connects

The test sites below use certificates from the compromised chains. If the tool connects, it still trusts the broken keys. If it gives a certificate error, it is protected.

10-second test (curl)

curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
# "SSL certificate problem" = protected
# showed the page          = EXPOSED

Node and Python, the same way

node -e "require('https').get('https://dv-g3b-emudhra.we-have-a-problem.com/',()=>console.log('EXPOSTO')).on('error',e=>console.log('protegido?',e.code))"
# EXPOSTO · or "protegido? UNABLE_TO_GET_ISSUER_CERT_LOCALLY" (certificate error code)

python3 -c "import certifi,ssl,urllib.request as u
try: u.urlopen('https://dv-g3b-emudhra.we-have-a-problem.com/',context=ssl.create_default_context(cafile=certifi.where())); print('EXPOSTO')
except Exception as e: print('protegido' if 'CERTIFICATE_VERIFY_FAILED' in str(e) else 'SEM TESTE', e)"

A network error (ENOTFOUND, timeout) is not "protected". When in doubt, use audita.sh.

Windows and macOS

audita.sh is for Linux. On Windows (PowerShell) and macOS (Terminal), the quick test is the same curl: curl.exe https://dv-g3b-emudhra.we-have-a-problem.com/ (Windows) or curl https://dv-g3b-emudhra.we-have-a-problem.com/ (macOS), and the same for the dv-g3b-aaa-emudhra chain. Certificate error = protected. If you have Node or Python installed, also run the tests above.

Test both chains. In our audit, several tools rejected the AAA chain and accepted the G3 one (or the other way around). A single test can give a false sense of security. And a network error (DNS, timeout) is not "protected": it is "no test".

The audita.sh script: everything at once, read-only

It tests the real connection with curl, wget, every Node found on disk (including Node embedded in tools), the system Python, every Python environment (venv) with its own certifi, and, from the inside, every running Docker container. It also lists outdated certifi and the Node and Go versions. It does not install, change or write anything.

1

Download the script and read it before running

Golden rule: never run a script from the internet without looking at what it does. This one has about 200 commented lines.

curl -fsSLO https://raw.githubusercontent.com/inematds/auditoria-seguranca/main/audita.sh
less audita.sh            # read it
chmod +x audita.sh

Or clone the repository: git clone https://github.com/inematds/auditoria-seguranca.

2

Run it on the machine

Without sudo it audits your user (and the containers, if you are in the docker group). With sudo it also sees other users' folders. The disk search takes up to 3 minutes; --rapido (quick) skips that part.

./audita.sh                 # full
sudo ./audita.sh            # includes Docker containers and other users
./audita.sh --rapido        # without searching the disk for venvs and Node
./audita.sh --sem-docker    # does not enter the containers

With sudo, the Node installed by your user's nvm is not in the default path; it is still found by the disk search (do not use --rapido in that case).

Example excerpt (the real output has more lines). G3 and AAA are the two "trust paths" tested: each site certificate is signed by an intermediate, which is signed by a root that your program trusts.

  • EXPOSTO (EXPOSED): it connected. Fix this layer (Update section).
  • protegido (protected): it refused with a certificate error.
  • SEM TESTE (NOT TESTED): the test could not run (network, DNS, timeout). Repeat before concluding.

Exit code: 0 nothing exposed, 1 there is EXPOSTO, 2 a test did not run. You can use it in monitoring.

4

Audit several servers over SSH

The script goes through SSH itself and runs there, without copying anything to the server. Use key-based access.

./audita.sh --ssh root@servidor1 --ssh deploy@servidor2

# or a list (one target per line; do not version-control this file)
./audita.sh --hosts servidores.txt
5

Fix, restart and run again

The audit only ends when the summary shows 0 EXPOSTO · 0 SEM TESTE on every machine. A process that was already running keeps the old list in memory: updating without restarting does not fix it.

How to update · layer by layer

Updating the system is not enough

Each tool may have its own list of trusted certificates. The system's ca-certificates protects curl and anything that uses the system list. Node, Python with certifi, Go, Electron, Rust and every container have their own.

1

System (ca-certificates)

# Ubuntu / Debian
sudo apt update && sudo apt install --only-upgrade ca-certificates
dpkg-query -W ca-certificates          # check the version
# Alpine
apk upgrade --no-cache ca-certificates
# Fedora / RHEL
sudo dnf upgrade ca-certificates

Keep automatic updates on (unattended-upgrades on Ubuntu/Debian). In our case, that is what fixed the system on its own.

2

Python: the certifi of each environment

requests and many packages use certifi, not the system list. Each venv has its own. audita.sh lists the outdated ones.

/path/to/venv/bin/python -m pip install -U certifi pip
python3 -c "import certifi; print(certifi.__version__, certifi.where())"  # 2026.10.19 or later
# tools installed with pipx / uv tool
pipx upgrade-all        # or: pipx runpip <app> install -U certifi
uv self update          # uv 0.13.4 or later
uv tool upgrade --all

Watch out for the "system" Python: if EXPOSTO shows up in certifi mode, there is a certifi installed with pip --user in your home folder (~/.local/lib/python3.X/). The path printed by the command above tells you which one. On Ubuntu 24.04 and Debian 12+ pip refuses to touch it ("externally-managed-environment"); since the change stays only in your user folder, use:

python3 -m pip install --user --break-system-packages -U certifi

The certifi from the system package (/usr/lib/python3/dist-packages) does not need this: on Debian/Ubuntu it points to the ca-certificates list.

3

Node: switch versions (Node 20 has no fix)

Node ships its list of certificates inside the program itself. Updating the system changes nothing for it.

# with nvm
nvm install 22 && nvm alias default 22     # 22.23.4 or later
# with the NodeSource repository (apt): it is separate per version.
# If you are on 20, switch the repository to 22 before installing:
curl -fsSLo nodesource_setup.sh https://deb.nodesource.com/setup_22.x
less nodesource_setup.sh                  # read it
sudo bash nodesource_setup.sh && sudo apt install -y nodejs
# already on 22 or 24? just update
sudo apt update && sudo apt install --only-upgrade nodejs
node -v

Stopgap for those who cannot switch today (tested by us): make Node use the already-updated system list. It only works if ca-certificates is fixed. --use-system-ca does not work: it adds the two lists together and was still EXPOSTO in our test.

export NODE_OPTIONS=--use-openssl-ca   # in the app's service/environment; then restart

NODE_OPTIONS is the environment variable that passes options to every Node started there (in systemd: Environment=NODE_OPTIONS=--use-openssl-ca; in Docker: the compose environment: section).

Also look for embedded Node: Playwright, AI agents and apps ship their own Node. audita.sh finds these binaries on disk; update the tool that brought them.

4

Go: update and recompile

An already-compiled Go program carries the old rule. Install Go 1.27.3 or 1.26.10 and build the binary again (go build). Third-party Go programs: update to the version they released after 10/21.

5

Docker: each container is a machine

A container does not use the server's ca-certificates. Old image = old list.

# ready-made images (from Docker Hub, GHCR...)
docker compose pull && docker compose up -d

# images you build: pull the new base and rebuild
docker compose build --pull --no-cache && docker compose up -d

In the Dockerfile, replace the node:20 base with node:22 (or 24) and update the list at build time:

FROM node:22-bookworm-slim
RUN apt-get update && apt-get install -y --only-upgrade ca-certificates && rm -rf /var/lib/apt/lists/*
# Alpine: RUN apk upgrade --no-cache ca-certificates
6

n8n: back up, then update

n8n runs on Node. Old version = old Node inside the container.

# 1) find the volume name (compose usually puts the folder name in front)
docker volume ls | grep n8n                 # e.g.: meuprojeto_n8n_data
# 2) stop n8n and make the backup (with it stopped, the database is not captured half-written)
docker compose stop n8n
docker run --rm -v meuprojeto_n8n_data:/data -v "$PWD":/bk alpine tar czf /bk/n8n-backup.tgz -C /data .
# 3) update
docker compose pull n8n && docker compose up -d n8n
Old docker-compose (1.29) trap: when bringing up the new image it may fail with KeyError: 'ContainerConfig' and leave n8n stopped. Remove the old container first (the data stays in the volume): docker-compose rm -f -s n8n && docker-compose up -d n8n. Even better: migrate to docker compose v2.

After updating, check the log (docker compose logs n8n). Big version jumps can bring new warnings, such as the one about the Python runner in the Code node.

7

Windows, macOS, phones and apps

  • Windows: Windows Update (Microsoft fix from 10/20).
  • macOS / iPhone: system update (Apple, 10/22).
  • Browsers: restart the browser to apply; Firefox 158.0.1 or later.
  • Electron apps (VS Code, Slack, Discord and others): update each app. For developers: Electron 44.9.1 / 43.8.1 / 42.11.16.
  • Rust: cargo update -p rustls-webpki -p webpki-roots and recompile.
8

Restart the services

A program that is already running held on to the old list in memory. Restart bots, APIs, workers, agents and n8n.

sudo systemctl restart <service>   # system services
pm2 restart all                     # Node apps managed by pm2
docker compose up -d                # containers: recreates with the new image

Note: docker compose restart only restarts the same container, with the old image. After pull or build, the right command is docker compose up -d.

And run audita.sh again.

Real case

We audited our servers. The system was fine. The rest was not.

In the early hours of 10/23/2026 we audited 6 servers with this method. No names or addresses: the pattern is what matters.

What was already right

The ca-certificates on all 6 servers had already been fixed by automatic updates. curl rejected the bad chains.

What was still exposed

Node, Python environments (certifi) and containers, including n8n, still trusted the broken keys.

What we fixed

  • Node 20 → 22
  • certifi in the Python environments
  • Node embedded in an agent
  • n8n 2.4.8 → 2.44.6 (with backup)
  • 4 containers rebuilt

Two infrastructure traps

1. Old docker-compose

n8n did not come up after the pull: docker-compose 1.29 raised KeyError 'ContainerConfig' with the new image and the service stayed down for a few minutes. Removing the old container before up solved it.

2. File mounted from /tmp

An nginx in a container mounted its configuration from a file in /tmp. Cleaning /tmp turned the path into an empty folder, and when the container was recreated nginx would not start. Mounted configuration has to live in a permanent folder.

And the development machine? We ran audita.sh on it too: the system and curl were protected, but the system Node, Playwright's embedded Node, the user's Python certifi, several Python environments and dozens of local containers (databases, dashboards, AI tools) still connected. Same pattern: anything that is not the system gets left behind. On an already-fixed server, the script still flagged an old Node in a forgotten backup folder (.bak) left over after the version switch: it was not running, but it is the kind of leftover someone executes by mistake. Delete old copies you do not use.
PHP2Shell

Your PHP site can be broken into without a password

PHP team advisory from 10/21/2026: two critical flaws allow running code on the server without logging in. The flaw is in PHP, before WordPress or any application even opens the page. A security plugin will not stop it.

The two flaws

  • CVE-2026-109618: the out-of-memory handling interrupts PHP with half-processed request data, and the cleanup treats that data as valid.
  • CVE-2026-109619: an internal request state survives after memory is freed, and the next request in the same process uses that stale state.

Who is exposed

  • Every PHP installation that serves pages: PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, LiteSpeed.
  • Higher risk with mod_php: there is a demonstrated attack that works before any application code runs.
  • PHP runs under about 7 in every 10 sites, including most WordPress ones.

Your case, in three situations

1. Ready-made platform

Shopify, Wix, Squarespace: PHP is the company's responsibility. Check the platform's security notice; if you cannot find one, ask support.

2. WordPress on shared hosting

Test the site (step below) and check the PHP version in the hosting panel. Below the fixed version: ask the provider to update today.

3. Your own server (VPS)

It is on you and it is urgent: attacks started even before the fix was out. Update, restart and look for signs of a break-in.

1

Test: the OpenAI checker

OpenAI published the php2shell-checker (Apache 2.0 license). It reads the version the site advertises in its headers; it does not send an attack.

git clone https://github.com/openai/php2shell-checker && cd php2shell-checker
node phpcheck.js "https://yoursite.com"
# OK (0) · POTENTIALLY VULNERABLE (1) · UNKNOWN (3)

Or ask your agent (Claude Code, Codex): "run php2shell-checker only against my site and explain the result". UNKNOWN is not a green light: the site hides its version; check in the panel or on the server.

2

On the server: check the real version

php -v
php-fpm8.3 -v                       # adjust the version number
apt changelog php8.3-fpm | head -30  # Debian/Ubuntu: look for CVE-2026-109618
Careful with the number. Linux distributions and long-term support (LTS) vendors received the fix earlier and may apply it while keeping the old number (backport). That is why the header and the checker cannot see a backport: "version below the fixed one" means "investigate in your vendor's changelog", not necessarily "vulnerable".
3

Fix: update and restart every process

  • Fixed versions: 8.5.12, 8.4.27, 8.3.36, 8.2.35 (or your distribution's fixed package).
  • PHP 8.1 and earlier no longer receive updates from the PHP project. Some distributions and LTS vendors have the fix: ask them or move to a supported version. Given the severity, the PHP team published minimal source-code fixes for 7.4, 8.0 and 8.1, for those who compile.
sudo apt update
apt list --upgradable 2>/dev/null | grep -i php   # see what will change
sudo apt install --only-upgrade 'php*'
sudo systemctl restart php8.3-fpm    # or apache2, if you use mod_php

Using the ondrej/php PPA repository (common for having several versions)? It also needs to carry the fixed version; check with php -v afterwards. mod_php is PHP running inside Apache; PHP-FPM is PHP as a separate service, used with nginx or Apache.

4

Cannot update right now? Reduce the exposure

The PHP team itself warns: these measures reduce known attack paths, they do not make the installation safe. Only updating fixes it. Apply them in php.ini, in the FPM pool or in the server configuration (not in ini_set() or .user.ini) and restart all workers.

# in the FPM pool (e.g.: /etc/php/8.3/fpm/pool.d/www.conf), which the application cannot change:
php_admin_value[memory_limit] = -1
php_admin_value[post_max_size] = 8M          # 32M if the site needs uploads
php_admin_value[upload_max_filesize] = 6M    # always below post_max_size
php_admin_flag[session.upload_progress.enabled] = off
# PHP 8.5 only:
php_admin_flag[fatal_error_backtraces] = off
  • memory_limit = -1 (against CVE-2026-109618) removes PHP's memory limit. This closes the attack path, but a buggy script can consume all of the server's RAM. That is why the PHP team recommends setting a limit outside PHP: the memory limit of the container (Docker) or of the service (cgroup, in systemd MemoryMax=), preferably killing only the affected process.
  • Do not use RLIMIT_AS/RLIMIT_DATA (ulimit memory limits) instead: they can trigger exactly the vulnerable out-of-memory failure.
  • session.upload_progress.enabled and fatal_error_backtraces turned off (against CVE-2026-109619) block only the confirmed paths, not other variants.
5

Were you exposed? Look for signs of a break-in

# .php files created or changed in the last 7 days inside the site
find /var/www -name '*.php' -mtime -7 -ls
# .php inside the WordPress uploads folder (there should be none)
find /var/www -path '*wp-content/uploads*' -name '*.php' -ls
# scheduled tasks you did not create
crontab -l; sudo crontab -l -u www-data; ls -la /etc/cron.*
# recent logins and new users
last -20; tail -5 /etc/passwd
wp user list --role=administrator   # WP-CLI, WordPress's command-line tool

Found something you did not create: take the site offline, change passwords and keys, restore from a backup made before the break-in.

What else is worth doing

Artificial intelligence is finding old flaws faster and faster. Defense is routine, not panic.

🤖 AI agents and curl | bash

  • An installer of the curl ... | bash kind runs code from the internet as your user. Download it first, read it, and only then run it.
  • Check the checksum (sha256sum file) or the signature published by the project.
  • Pin versions (package-lock.json, requirements.txt with versions, Docker images with tags) and update on purpose, not by accident.
  • Agent with terminal access: run it in an isolated folder or container, with no secrets in sight.

📅 Monthly checklist (30 minutes)

  • System updates applied and automatic updates on.
  • Node, Python (certifi), Go and Docker images on supported versions.
  • ./audita.sh on every machine: summary at zero.
  • Backup tested: you actually restored it, not just "it exists".
  • Version line still supported (Node 20 and PHP 8.1 no longer are).

🔎 Watch your domain's certificates

Every issued certificate lands in a public log (Certificate Transparency). Search for your domain on crt.sh and see whether a certificate you didn't request has appeared. A CAA record in DNS says which certificate authorities may issue for your domain.

dig CAA yourdomain.com +short

⚙️ CI/CD and secrets

  • Rebuild images in the pipeline with --pull: a stale cached image brings a stale list.
  • Run audita.sh as a deploy step; an exit code other than 0 blocks the deploy.
  • No keys in code or in git (.env outside the repository); if a key leaked, rotate it, don't just delete it.
  • For websites, INEMA's blinda-site method looks at headers, dependencies, secrets and the database with an AI agent, without touching the live site.
Glossary

The words in this guide

Certificate authority (CA)

A company that signs HTTPS certificates. It is the "notary" that says: this site really is who it claims to be.

Root, intermediate, chain

The root is the parent signature your program trusts. It signs intermediates, which sign the sites. The sequence is the chain. The leaked keys belong to intermediates.

P-384

A type of elliptic-curve key. A good P-384 key is a number with more than 100 digits; eMudhra's were smaller than 256.

ca-certificates

A Linux package with the system's list of trusted certificate authorities. Used by curl, wget and many programs.

certifi

A Python package with its own list of certificate authorities. requests uses it, not the system's.

venv

An isolated Python environment for a project, with its own packages (and its own certifi).

Container (Docker)

A lightweight "machine" inside the server, with its own system and certificate list. Old image = old list.

pm2 · systemd

Managers that keep programs running on the server and restart them.

CVE

A public number for a security flaw, used to look up the fix (e.g.: CVE-2026-109618).
